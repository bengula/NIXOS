# NixOS Configuration

My NixOS configuration, organised with the **Dendritic Pattern**: flake-parts
plus `import-tree`, where every `.nix` file under `flakes/modules/` is a
flake-parts module that gets loaded automatically. There is no import list to
maintain — a file becomes part of the system by existing.

```bash
sudo nixos-rebuild switch --flake ./flakes#Erudite
```

> This is a git flake, so Nix only sees **tracked** files.
> After adding a module: `git add flakes/modules/your-file.nix`, then rebuild.

---

## How it is put together

`flakes/flake.nix` is the whole entrypoint:

```nix
outputs = inputs:
  inputs.flake-parts.lib.mkFlake { inherit inputs; } (inputs.import-tree ./modules);
```

Each file under `modules/` describes one **aspect** of the machine, and an
aspect can contribute to more than one module class at once:

| What you write | What it becomes |
|---|---|
| `flake.modules.nixos.<aspect>` | a NixOS module |
| `flake.modules.homeManager.<aspect>` | a Home Manager module |

`modules/terminal.nix` is the clearest example: one file owns both the system
package and the user's terminal profile, so the terminal is described in one
place instead of two.

Aspects are only *published* by these files — nothing is switched on until
`modules/hosts.nix` picks it up. That file is the single place that says what
the machine is made of.

### Adding something

Drop a file in `modules/`:

```nix
# modules/gaming.nix
{
  flake.modules.nixos.gaming = { pkgs, ... }: {
    programs.steam.enable = true;
  };
}
```

then add `nixos.gaming` to the list in `modules/hosts.nix`, `git add` it and
rebuild. A second machine later means a second entry in `hosts.nix` reusing the
same aspects — that is the point of the pattern.

## Hyprland: key suggestions

You should never have to remember a shortcut you have not learned yet. Three
things make the keymap discoverable, and all three are generated from the
**same list** in `modules/hyprland-keys.nix`, so they cannot drift apart:

### 1. `Super + /` — searchable palette

Opens every binding in wofi. Type to filter. Pressing **Enter runs the action**,
so it works as a command menu when your hands have forgotten the key. Also on
`Super + F1`, and on the **keys** button in the bar.

### 2. Which-key modes

Press once, then use single keys. The available keys appear on screen as a
notification, and waybar shows which mode you are in until you leave it.

| Key | Mode | Inside the mode |
|---|---|---|
| `Super + R` | Resize | `h j k l` / arrows resize · `Shift` for big steps |
| `Super + W` | Window | `h j k l` move · `f` fullscreen · `v` float · `q` close · `p` pseudo · `t` split |

`Esc` or `Return` returns to normal.

### 3. A nudge at login

The first notification after logging in points at `Super + /`.

## Idling and locking

`modules/lock.nix` also owns the idle timeline, staged so nothing happens
without a warning you can undo by touching the machine:

| After | What happens |
|---|---|
| 5 min | Screen dims (the old brightness is saved and restored) |
| 10 min | `loginctl lock-session` → `hypr-lock` |
| 15 min | Display off |

`hypr-lock` is the single entry point, so the idle timer, the lid switch and
`Super + Escape` all take the same path — including the wallpaper exit/intro
sequence below, and including the `loginctl` bookkeeping: `hypr-lock` sets
`LockedHint` once hyprlock is on screen and clears it on unlock, so anything
watching logind's `Lock`/`Unlock` signals sees the same thing on all three
paths. `Super + Escape` deliberately does *not* go through
`loginctl lock-session` — that would make the lock key a no-op whenever
hypridle is not running.

hypridle is bound to `hyprland-session.target`, not
`graphical-session.target`, because GNOME does its own idle handling and two
of them fighting is worse than either.

## Animations

Two separate animation systems, because hyprlock does not use Hyprland's.

**The session** — `modules/desktop-hyprland.nix`. Durations are in 100ms units.
Entrances use a curve that overshoots slightly and settles (`overshot`); exits
use one that accelerates away (`smoothOut`) and run shorter, because a window
taking as long to leave as it took to arrive feels sluggish. Workspaces
slide-fade, the special workspace drops in vertically, and `layers` gives the
bar, launcher and notifications a slide instead of a blink.

`borderangle, 1, 100, liner, loop` rotates the active window's gradient border
on a 10-second cycle. It repaints continuously — delete that one line if you
would rather have the battery.

**The lock screen** — `modules/lock.nix`. hyprlock has its own animation tree
(`fadeIn`, `fadeOut`, `inputFieldColors`), so the lock/unlock transition is
configured there. Locking fades in over half a second; unlocking clears in
three tenths, since the way back to work should not make you wait.

## The wallpaper

`modules/wallpaper.nix` runs [Orbit Wallpaper
Engine](https://github.com/CleanShirtUK/orbit-wallpaper-engine) — a GLSL
fragment shader drawn on the background layer — in place of hyprpaper.

The interesting part is that it listens on a control FIFO at
`~/.cache/orbit-wallpaper-engine/control` and takes three commands: `intro`,
`exit` and `palette`. That is what makes locking feel like an event:

```
Super + Escape → hypr-lock
      hyprlock starts, screenshots the live desktop
      0.4s later → "exit"   the wallpaper animates away behind the lock screen
      you unlock
                 → "intro"  4.5s reveal as the desktop comes back
```

Every one of those signals is optional and time-bounded — a missing FIFO is a
no-op and a write with no reader gives up after half a second. A cosmetic
wallpaper must never be able to wedge a lock screen, so `hypr-lock` degrades
to plain hyprlock if the renderer is not running.

The renderer is a systemd user service bound to `hyprland-session.target`
rather than `graphical-session.target`, because it needs `wlr-layer-shell` and
must not try to start when you pick GNOME at GDM.

**Shaders.** `wave.frag` ships with the engine and is the default. Drop further
`.frag` files into `~/.config/orbit-wallpaper-engine/shaders/` and point
`ORBIT_WALLPAPER_SHADER` at one. The upstream shader browser pulls from the
[KDE Shader Wallpaper](https://github.com/y4my4my4m/kde-shader-wallpaper)
catalogue, but it needs Quickshell, which is not installed here — fetching a
`.frag` by hand does the same job.

**Iterating on the build.** The renderer builds on its own:

```bash
nix build ./flakes#orbit-wallpaper-engine
```

which is much faster than a full `nixos-rebuild` when something fails to
compile.

## The translucent terminal

GNOME Terminal keeps profiles in dconf, so `modules/terminal.nix` pins a fixed
profile UUID and writes it declaratively. Transparency needs two settings, not
one — `use-theme-transparency` must be **off** or the GTK theme overrides the
percentage:

```nix
use-theme-transparency = false;
use-transparent-background = true;
background-transparency-percent = 22;   # 0 = opaque, 100 = invisible
```

Transparency on its own just makes text unreadable, so Hyprland does the other
half of the work in `modules/desktop-hyprland.nix`: three-pass blur with a
contrast bump, plus `layerrule` entries so the bar, the launcher and
notifications sit on the same frosted surface. Adjust the percentage and the
`decoration.blur` settings together — they are two halves of one look.

## Key features

## Hardware

`flakes/hosts/erudite/hardware.nix` is generated by `nixos-generate-config` —
update it cautiously. `modules/hardware-erudite.nix` publishes it as an aspect
so `hosts.nix` can consume it like anything else, and sets
`hardware.enableRedistributableFirmware`, which the generated file's Intel
microcode line depends on.

## Rough edges

Known and deliberate, listed so they are not rediscovered as surprises.

- **`flake.lock` needs regenerating.** It predates the `flake-parts`,
  `import-tree` and `orbit-wallpaper-src` inputs. Run `nix flake update` (or
  `nix flake lock`) in `flakes/` and commit the result, otherwise every rebuild
  re-resolves those three inputs from the network and the config is not
  reproducible.
- **`pkgs/bengula-portal.nix` still has `npmDepsHash = lib.fakeHash`.** Harmless
  while `services.bengulaPortal.enable` is false — the derivation is never
  forced. Fill it in before switching the portal on; see the comment in the file.
- **`boot.loader.grub.device = "/dev/sda"`.** Kernel disk names are not stable
  across hardware changes. `/dev/disk/by-id/…` would be safer, but getting it
  wrong makes the machine unbootable, so change it deliberately and keep the
  previous generation around.
- **`networking.nameservers` hardcodes Google DNS**, which overrides whatever
  DHCP hands out. That breaks captive-portal logins on café and campus Wi-Fi
  and hides local `.lan` names. Delete the block to fall back to DHCP.
- **`services.openssh.enable = true`** opens port 22 with password
  authentication on by default. Fine on a trusted LAN; on public Wi-Fi, either
  turn it off or add keys to `users.users.<name>.openssh.authorizedKeys.keys`
  and set `services.openssh.settings.PasswordAuthentication = false`.
